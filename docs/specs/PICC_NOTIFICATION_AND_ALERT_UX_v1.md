## Design

### Decision A — manifest: `apps/dashboard/public/manifest.json`, standard Vite publicDir copy

The manifest belongs in `apps/dashboard/public/` next to the only other static asset, `sw.js` (`apps/dashboard/public/sw.js`). Vite copies `public/` into `dist/` by default, and the production server serves `dist/` with a `.json → application/json` MIME entry already present (`index.mjs:16,23`). The two real risks are (a) a Vite publicDir config that disables the copy, and (b) the SPA fallback (`index.mjs:78-86`) silently serving `index.html` for a missing manifest — T1 must assert the round trip (`resolveStatic` at `index.mjs:30-41` path-normalizes `/manifest.json` to `dist/manifest.json`). Icon files: 192/512 PNGs land in `public/icons/`; the existing inline-SVG favicon (`index.html:7-10`) stays.

### Decision B — payload v2: additive whitelist, actions attached by the SW

`notifier.mjs` webpush body (`notifier.mjs:109-114` — today `{title, body, asset, kind}`) gains `venue`, `windowText`, `actions`, `requireInteraction: false`. The SW (`sw.js:17-36`) whitelist-parses each field (never passes through raw JSON — the existing per-field parse pattern at `sw.js:20-24` is the model, extended field-by-field with length caps), then calls `showNotification` with `actions` and `requireInteraction` attached and `data.url` pointing at the deep link computed per REQ-4. `notificationclick` becomes an `event.action` switch (`sw.js:38-48`). This keeps the SW dumb and the payload honest: actions are best-effort UX sugar (web.dev feature-detection note: `'actions' in Notification.prototype`; macOS Safari/Firefox don't render all buttons — the click fallback below covers it).

### Decision C — snooze: a notifier-owned persisted ledger, NOT an alertEngine primitive

Verified this session: `alertEngine.mjs` has no delay/snooze primitive, so the plan's "reuse whatever backs alertEngine's existing scheduling" is not available. Snooze lives in the notifier (the only module with persisted state, `notifier.mjs:21,24-39`): `state.snoozes = { [tag]: { dueAt, count: 1, payload } }` persisted via the existing atomic persist (`notifier.mjs:44-57`). A `flushSnoozes()` sweep runs on a `30_000` ms interval started beside `startSignalEngine()` at `index.mjs:156` (new exports `startSnoozeFlusher`/`stopSnoozeFlusher`, mirroring `stopSignalEngine` at `signalEngine.mjs:182-186`). Because the ledger re-dispatches through `dispatchAlert` (`notifier.mjs:181-199`), every channel gets the re-show, per-channel results stay honest, and `recent[]` records the re-show with its original `ts` plus a `snoozed: true` marker. The one-shot rule (REQ-5) is enforced by deleting the ledger entry at flush time.

### Decision D — deep-link venue field: resolved at dispatch, from the sensor-covered set

`signalEngine.mjs` gains a venue-resolution step before `dispatchAlert`: query the SAME venue catalog the studio browser scans (`captureProfiles.mjs` `studioCaptureCatalog()` — successor to the removed `extensionCaptureConfigs()`) and, for the alerting asset, resolve each candidate via `instrumentUrl` (`browserStudio.mjs:573-582`, mode per `browserStudio.test.mjs:68-89`). If exactly one candidate has `mode !== "none"`, set `venue = { venueId, tradeUrl }`; else omit. This intentionally ties the deep link to venues PICC can actually open with the studio (today: ExpertOption live via `liveEO`), so the pattern never deep-links into a venue with no live feed.

### Decision E — deep-link handling: react-router `useSearchParams`, flat-stack anchor

Verified: `MarketsSuite` is a flat panel stack (`TradingSuite.tsx:107`, panels at `:187-206`) — there is NO tab system, so the plan's `panel=chart` cannot map to a tab switch. Mapping: `panel=chart` scrolls to/focuses the chart panel (a `panelAnchor("chart")` DOM helper on `MarketsSuite`'s chart container from the plan's original `panelAnchor()` sketch), and `asset` feeds the existing `chartAsset` state (`TradingSuite.tsx:114,173`). `react-router-dom` is already the app's router (`TopBar.tsx:1`, `AppShell.tsx:2`), so `useSearchParams` is the natural read; the suite component is rendered inside the router tree. Venue opening goes through the studio bridge (Decision G) with `window.open(tradeUrl)` as the no-studio fallback.

### Decision F — iOS install guidance: extracted pure function + one surface

A new `lib/installEligibility.ts` exports `isIOSInstallNeeded(userAgent, isStandalone)` (pure, vitest-covered) implementing the 2026 iOS rule set: iOS detected AND (`navigator.standalone`-style standalone flag false OR version < 16.4) → banner; the installed-PWA-only constraint is why `display:"standalone"` in the manifest (REQ-1) is a hard requirement for push-enabled iOS users. The bell/subscribe surface (`NotificationCenter.tsx:139-141`, per `PICC_TRADING_SUITE_UPGRADE.md` REQ-8) and suite both use the function — no second opinion anywhere in the app.

### Decision G — `studioTab "open"`: dashboard → studio bridge → venue tab

The extension `open-broker-tab` mechanism this decision originally specified was superseded by decision D2 (A-3) with the D1 clean break (2026-09-17): the browser extension is gone, so there is no content-script bridge (`content.js`, `chrome.runtime.sendMessage`) and no chrome-action vocabulary to pin. The dashboard now sends `studioTab {action:"open", url}` over the studio bridge (`browserStudio.mjs`); the studio finds an existing venue tab by hostname (trailing-slash-insensitive) and focuses it, else opens one via its pages API — returning `{ok, found}` so the dashboard can fall back to `window.open(tradeUrl)`. No host-permission story remains (there is no extension manifest to constrain) beyond the studio's own pages access, and the D2 contract forbids session/token material in any RPC payload. Cross-check the exact `studioTab` shape and test pin in `browserStudio.test.mjs` (renamed/extended during A-3) before coding.

### Decision H — email removal: code first, docs second, prefs migration tolerance

Removal sites (all verified this session): `notifier.mjs:8` (doc line), `:132-148` (`sendEmail`), `:173` (channel row); `handlers.mjs:2551` (capabilities row); `CapabilitiesPanel.tsx:79-81`; `notifier.test.mjs:15,48,59`; `.env.example:160-163`; `TradingSuite.tsx:868` test-dispatch message ("check bell/email/push" → "check bell/push."); historical docs `MTF_CONVERGENCE_ENGINE.md:26` and `TRADING_SUITE_GENERALIZATION_SPEC.md:638,640,724-737,759,875` get a removal note (T10). Verified NOT present (the master plan named them — they are false): `docs/SETUP.md` and `docs/TRADING_RUNBOOK.md` contain zero Resend/notification env references. `resend` is not a package.json dependency (grep this session), so there is no uninstall step. `setPrefs` iterates patch keys (`notifier.mjs:65-72`) and `SignalNotificationsCard` renders channels from `notifierStatus()` (`notifier.mjs:201-213`), so removing the channel auto-removes its row; a persisted `channels.email` key is simply never read again — inert (REQ-11).

## Non-goals

- **No execution weld.** Nothing in this spec places an order anywhere. Deep links open venues and focus tabs; the advisory-only posture (`signalEngine.mjs:16` "Nothing here places orders anywhere", `PICC_FULL_SCOPE.md` guardrails) is unchanged.
- **No studio-host reach beyond venue tabs.** The studio bridge's tab handling is limited to find-or-create on the target venue's `tradeUrl` (Decision G); no session/token material in any RPC payload (D2 contract). The extension host-permission story (`manifest.json:12-15` localhost-only) is moot — no extension manifest exists since the D1 clean break.
- **No live countdown in push.** Push body copy is static (REQ-7); countdown is in-app only (REQ-8).
- **No custom snooze durations.** Fixed 10-minute snooze (REQ-5), one-shot per tag. No snooze presets UI.
- **No Wave-1 execution restoration build.** Master-plan Part 1 reframing (dormant vs assisted-with-great-alerts target) is a DECISION ticket, not a build ticket — this spec only builds the "great alerts" half.
- **No companion flaky-test fix.** `useCandleData.render.test.tsx` (uncommitted modification in the working tree this session) stays a separate diagnosis ticket.
- **No mobile app / background-sync / widget surface.** iOS PWA push (16.4+) is the mobile reach; Background Sync is not a WebKit capability (2026 iOS constraints).
- **Deriv adapter and the finance-tracker frontend** (master-plan Part 5) are referenced, not built.
